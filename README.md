# Golden Skills

本仓库用于沉淀、试用和改进我自己反复使用的skills。目标是把我自己实践过的、有用的做事方式留在仓库里，形成个人工作流。

## 为什么需要 Skill

**模型有能力完成任务，不等于每次都会按你的标准完成。** Skill 的价值不是重复通用知识，而是提供模型无法凭空知道的工作方法、约束和判断标准，减少反复解释。

以代码检视为例：模型可能看得懂代码、识别常见缺陷，却仍需明确检视范围和版本基准、项目契约，以及是否讨论风格和设计建议。这些要求未必能从代码中推导出来，也没有唯一正确答案。

Skill 主要解决三件事：

- **复用上下文**：把反复说明的要求保存下来，例如沿调用链分析、说明触发条件、不把个人风格当作缺陷。
- **提高一致性**：显式列出关键判断和完成标准，减少遗漏与执行漂移，但不保证模型严格执行。
- **积累方法**：根据真实任务中的漏项和错误修订规则，让经验影响下一次执行，而不只停留在一次对话中。

Skill 不是越多越好。模型默认就能稳定完成的任务，不必另写 skill；一次性需求直接提问即可；确定性的检查优先交给编译器、静态分析或脚本。过时、冗长或僵化的规则反而可能干扰模型判断。

本仓库优先沉淀的是：**值得反复复用、又不能指望模型默认知道的工作方法。** 例如，代码检视 skill 不应只是“检查空指针、内存泄漏”的常识清单，而应明确如何界定问题、要求什么证据、怎样取舍，以及何时算完成。

## Skill、笔记与 Wiki 的边界

**笔记记录学到了什么，Wiki 整理已经知道什么，skill 固化希望 AI 如何做事。** 三者都可以用 Markdown 编写；区别在用途，不在文件格式。

| 维度 | 笔记 / Wiki | Skill |
| --- | --- | --- |
| 核心问题 | 是什么、为什么、有哪些依据 | 遇到这类任务，应该怎么做 |
| 组织中心 | 主题、概念、项目及其关联 | 触发场景、输入、决策规则、行动和交付 |
| 使用方式 | 由人或 AI 搜索、阅读、引用 | 由 Agent 根据描述或显式调用加载，指导任务执行；具体发现机制取决于客户端 |
| 完成标准 | 内容准确、清晰、可追溯 | 能指导真实任务，产出符合要求且可验证的结果 |
| 更新依据 | 新知识、新证据或理解变化 | 实践暴露的漏项、错误判断或无效步骤 |

例如，代码检视相关内容可以这样分工：

- **笔记 / Wiki**：解释资源生命周期、并发安全、数值精度等原理，保存历史问题、论据和反例。
- **Skill**：明确检视范围和基准，追踪受影响的调用路径，依据证据判断问题，按严重程度输出问题位置、触发条件、影响及验证方式；需要领域知识时再引用参考资料。

个人观点也可以成为 skill 的依据，但应转化为**适用条件、判断规则、例外和验证方式**。例如，“性能比抽象重要”是立场；“检视执行热路径时检查新增分配、复制和重复计算，性能结论需有测量或执行路径依据；冷路径不机械套用”才是可执行的规则。尚未验证的观点应标为假设，而不是强制规范。

Wiki 也可以包含操作手册，有步骤并不意味着它一定是 skill。只有当内容需要被 Agent 用来执行一类任务，并明确了触发条件、输入要求、决策规则和交付标准时，才值得提炼为 skill。给笔记补上 YAML frontmatter，并不能证明它能有效指导任务。

仓库优先保存可复用的工作方法，而不是把所有知识都包装成 skill：

- 可重复执行的流程放在 `skills/<name>/SKILL.md`，一个 skill 聚焦一类任务。
- 执行时才需要的知识或标准可放在该 skill 的 `references/`；已有 Wiki 则直接引用，不复制维护多份。
- 原始学习笔记、一次性调试记录和未成形的观点保留为普通笔记，不必放进 `skills/`。

Skill 是自然语言指导，不是确定执行的程序。需要用真实任务检验其效果，不能仅凭格式校验判断有效。

## 从任务到 skill

1. **记录案例**：写清输入、想要的结果、实际做过的步骤，以及哪里容易出错。优先挑选已经重复发生的任务。
2. **提炼规则**：保留会影响下一次决策的经验，例如信息来源、判断标准、工具选择和完成标准。一次性的项目细节留在案例里，不写成通用命令。
3. **编写 skill**：在 `skills/<name>/SKILL.md` 写清触发场景、目标和关键约束；需要时再加 `references/`、`scripts/` 或 `assets/`。一个 skill 解决一类明确的问题。
4. **验证**：运行 `python3 scripts/validate_skills.py`，再用一个真实但可控的任务试用。根据实际结果做小幅修订。

## 现有技能

- [`code-review`](skills/code-review/SKILL.md)：设计优先，以一次变更为入口，只读检视 MindSpore Lite LLM 及受影响存量模块。输出“必须修改／建议修改／可选改进”，标明来源和确信程度；验证由提交者负责，不改代码、不发布评论。

使用示例：“用 `skills/code-review/SKILL.md` 检视 MindSpore Lite LLM 的这次分支变更，以指定目标分支为基准，同时关注受影响的存量模块。已有验证材料随请求提供；缺少时请指出具体需要补充的用例与结果。”

检视顺序为“需求与影响范围 → 整体设计 → 实现细节”。主技能只保留关键流程与标准，[专项清单](skills/code-review/references/checklists.md)按影响选择。清单吸收 llama.cpp 的设计、安全、模型适配、后端及接口检视方法，不移植其专属 API 或社区政策；有充分依据的设计问题即使尚无行为缺陷，也可以要求必须修改。

[代码坏味道](skills/code-review/references/code-smells.md)参考覆盖散弹式修改、时间耦合、抽象泄漏、冗余状态等设计线索，每项给出识别信号、需核实的证据、合理例外与改进方向。坏味道不直接等于缺陷，也不自动要求重构。

`code-review` 尚未经过真实检视案例校准；格式校验和静态场景检查不代表实际检视效果已验证。

## 仓库结构

```text
skills/
  code-review/
    SKILL.md
    references/
      checklists.md
      code-smells.md
scripts/
  validate_skills.py
AGENTS.md
```

每个 `skills/<name>/` 都是一个独立的 skill。新增内容应尽量小；确实需要固定操作或较长资料时，再增加脚本或参考文件。

## 在 Codex、Claude Code 和 oh-my-pi 中使用

`skills/` 是维护源，不是所有客户端默认扫描的目录。在本仓库中可以直接要求 Agent 读取 `skills/<name>/SKILL.md`；要在其他项目中发现和使用技能，将完整技能目录复制到对应客户端的用户级目录。

| 客户端 | 用户级安装目录 | 显式使用方式 |
| --- | --- | --- |
| Codex | `~/.codex/skills/<name>/` | 在请求中指定技能名称 |
| Claude Code | `~/.claude/skills/<name>/` | `/<name>`，例如 `/code-review` |
| oh-my-pi | `~/.agents/skills/<name>/` | `/skill:<name>`，例如 `/skill:code-review`；需启用技能命令 |

在仓库根目录执行所需客户端的安装命令。以下以现有的 `code-review` 为例，只需选择对应的一组：

```bash
# Codex
mkdir -p ~/.codex/skills
cp -R skills/code-review ~/.codex/skills/

# Claude Code
mkdir -p ~/.claude/skills
cp -R skills/code-review ~/.claude/skills/

# oh-my-pi：使用默认加载的 Agents 技能目录
mkdir -p ~/.agents/skills
cp -R skills/code-review ~/.agents/skills/
```

复制整个目录，保留 `references/`、`scripts/` 等相对路径依赖。安装后重新开启会话，尝试显式调用，并检查 Agent 是否读取了对应技能。oh-my-pi 若未启用技能命令，可直接要求它读取 `skill://code-review`。

仓库仍是维护源；复制安装不会自动同步更新。修改技能后需重新复制；若删除或重命名了文件，还需清理安装副本中的旧文件。不要直接修改安装副本，也不要无意覆盖其他来源的同名技能。

客户端的发现和调用机制参见 [Claude Code 技能文档](https://code.claude.com/docs/en/skills)与 [oh-my-pi 技能文档](https://github.com/bit-cook/oh-my-pi-coding-agent/blob/main/docs/skills.md)。通用技能内容可以复用，但客户端专属工具或语法仍需分别验证。

首次沉淀某类任务时，尽量给出真实例子。完成一次新任务后，补充“这次哪些判断值得复用、哪些只是个例”，比不断堆长规则更有用。
