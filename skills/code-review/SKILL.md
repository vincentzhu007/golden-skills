# MindSpore Lite LLM 代码检视

## 边界

- 只读代码、diff、历史、文档、测试代码和提交者提供的结果；可做只读 Git 查询及代码导航。不改代码、不写 PR 文案、不发布评论。
- 不执行构建、测试、最小复现、推理或基准，不安装依赖、不改环境、不操作设备、不触发远端任务。
- **验证是提交者的职责**：提供用例、执行条件与结果，支持正确性、精度及性能主张。评审者审查证据，不代为执行；测试代码不等于通过结果，缺少证据也不等于代码必然错误。

## 顺序

1. **明确需求与范围**：从请求和仓库确认变更集、比较基准、是否包含未提交修改及适用规范；不假设主分支，不混入无关改动。读完整 diff，沿数据流、控制流、状态和资源生命周期追踪调用者及存量实现，必要时跨模块；只问无法从现有信息确定的事项。
2. **设计优先**：先判断方案是否合理，再深入实现。行为正确不代表设计良好；检查职责、状态模型、所有权、现有能力复用和复杂度。设计问题可以要求必须修改，但须有具体代价、代码依据、可行替代方向及取舍，不能仅凭个人偏好。
   设计检视时读取 [代码坏味道](references/code-smells.md)，按“现象 → 成因 → 代价 → 最小改进”建立证据；坏味道只是线索，不自动要求重构。
3. **关联存量**：本次变更加重存量设计问题时，可要求先做最小必要调整，说明因果关系和范围；无关历史债不绑入本次变更。简单方案必须满足明确需求，不能自行削减功能。
4. **深入检查**：读取 [专项清单](references/checklists.md)。每次检查设计、安全与资源、通用规范及材料；按实际影响选择模型/LLM 状态、后端/算子、公共接口/服务专项，简述选择原因。设计优先不替代正确性、安全、性能和风格检查；不机械填满清单。
5. **核对证据**：追踪结论所需代码，检查调用约束和已有保护，区分事实、推导、假设及提交者陈述。需要补证时说明具体用例、条件或结果及要排除的风险，交由提交者完成。

## 表达与输出

开头说明比较基准、已覆盖模块与关联路径、材料限制，并明确“本次仅静态检视，未执行验证”。私有检视意见按以下三类组织，类内优先列出影响较大的问题：

| 分类 | 标准 |
| --- | --- |
| **必须修改** | 影响本次变更安全合入的行为或设计问题，或明确违反合入要求；说明阻塞依据。存量问题只有确实影响本次变更时才阻塞。 |
| **建议修改** | 有具体收益的规范、设计或验证改进，但不足以判定必须阻塞。 |
| **可选改进** | 轻微风格、局部清理等；纯个人偏好只能归入此类。 |

每条给出**标题、文件与行号或符号、来源、确信程度、依据与影响、建议方向或补证要求**。位置可在关联存量代码，不强贴修改行。同一根因合并，不空列模板或凑数。

- **来源**：变更引入或暴露（说明因果关系）／相关存量（不误归因）／改进建议（不冒充缺陷）。
- **确信程度**：高——完整静态路径和明确契约，或与代码相符的提交者复现材料支持；中——有证据但依赖未确认条件，必须写明条件及确认方式；低——关键证据不足，只将值得继续核实的事项单列“待核实事项”，不列为正式缺陷。确信程度与影响及处理分类分开，不用未经校准的百分比。
- **风格依据**：仓库明确规范 → 模块惯例 → 个人偏好；标明依据，同类建议合并，不把偏好当作项目要求。
- **措辞**：准确描述条件、路径和后果，不随意发布“可能有风险”等模糊观点。无法确认调用方会复用失败会话时，应提出条件式风险及所需证据，不能断言后续请求必然出错。

末尾按需列待核实事项及提交者需补充的材料，避免重复。没有发现时只说“在本次已覆盖范围内未发现可报告问题”，不声称代码已验证正确。

完成前确认：设计及实现均已检视，结论有依据且已考虑反证，分类与确信程度恰当，验证责任未越界。本技能尚未经真实检视案例校准；格式校验不证明检视效果。
