# 按影响选择检视清单

从 llama.cpp 的检视方法中提炼通用检查，不移植其专属 API、命名、目录或社区政策。具体契约以 MindSpore Lite 的代码、文档和适用规范为准。以下检查均为静态分析；用例执行及结果由提交者提供。

## 设计优先（每次）

- 明确需求、非目标和变更理由：方案是否解决真实问题，是否混入无关工作；只有项目规范明确要求时，才将缺少 issue 或设计讨论视为合入问题。
- 先查现有机制与类似实现，再判断新增组件、依赖、配置或公共接口是否必要。已有能力能否通过较小调整满足需求，避免平行实现和相似模型的大段复制。
- 从数据模型、状态和职责审视方案，是否可以消除一层机制，而不是在当前方案上继续叠补丁；不要把行为正确当成设计合理的充分条件。
- 所有权与生命周期是否清晰；手工存活标记、重复状态转换或多处同步维护同一事实是否有必要。比较替代方案时说明实际收益、迁移成本和兼容影响，不机械要求特定抽象。
- 模型或设备特例是否侵入通用路径；实际差异若是能力或配置，是否错误地按模型名、架构名或设备名分支。
- 本次变更若加重存量设计债，可要求先做最小必要调整；说明关联性和范围，无关设计债不绑入本次修改。
- 满足明确需求后再比较简单性。不能自行舍弃必要功能以换取“简单方案”；需要缩小需求时交给用户决定。

## 安全、边界与资源（每次检查适用路径）

- 确认模型文件、元数据、张量形状、配置和请求字段的信任边界。检查来自外部的数据，而不是无依据地宣称任意变量均可被攻击者控制。
- 尺寸、步长、偏移和字节数的乘加及对齐运算，是否在溢出发生前检查；不能在已回绕后才比较结果。
- 长度、层数、token ID、枚举及其他索引是否在访问前校验；声明长度与实际数据是否一致，必需检查是否被可选字段或空缓冲分支绕过。
- 窄化转换、有符号/无符号混算、负值和解析异常是否绕过边界；派生值和默认值同样需要满足使用处契约。
- 缓冲区重用、缩小或重分配后，容量、有效长度和缓存指针是否仍一致；容量预留不等于元素已存在。
- 异步路径是否在完成前释放输入或输出；是否保存临时或调用方存储的裸指针；失败、取消、重置和释放后是否遗留悬空引用、资源或请求状态。
- 先核实保护逻辑与真实执行模型再报告。安全疑虑也需要触发路径和确信程度，不能仅凭检查项名称判定“必须修改”。

## 模型适配与 LLM 状态（相关时）

- 配置、权重命名映射、形状与类型是否沿现有加载及转换机制一致传递；运行必需的字段缺失时是否错误地静默使用默认值。
- 近似架构能否复用现有实现；若选择复制，差异是否真实且值得独立维护；保留必要的模型语义说明，移除适配后的死分支。
- prefill/decode 的位置、掩码、长度、批次与 KV Cache 是否保持一致；追踪创建、扩容、复用、重置和释放，检查失败后重试及跨请求状态。
- 相关量化权重、量化 KV Cache 或可选特性是否仍满足契约；不能凭默认精度路径正确就推广到其他配置。要求提交者提供实际受影响组合的用例及结果，不强加固定后端数量。
- RoPE、采样、图构建或多模态预处理发生变化时，检查能否复用现有原语，新增实现是否有必要；不能直接指定 ggml 的实现作为 MindSpore Lite 的要求。

## 后端、算子与性能（相关时）

- 能力声明、分派和回退条件是否精确覆盖目标类型、形状、布局与设备，是否无意启用不支持的组合或禁用其他路径。
- 张量布局、步长、对齐、数据类型、设备内存及同步契约是否贯通调用链；硬编码执行宽度或设备参数是否破坏其他受支持设备。
- 后端为局部优化修改共享图或状态时，是否越过职责边界、影响其他消费者；检查实现方式而不一概禁止图变换。
- 热路径新增分配、复制、同步、重复计算或过度模板化是否必要；区分可由代码证明的额外工作与需要测量的性能退化。
- 新算子、内核或优化需提交者提供受影响形状、设备、配置及基准结果；精度比较说明指标、容差和参考实现。只审查材料，不执行测量，不虚构性能结论。

## 公共接口与服务边界（相关时）

- 新接口为何不能由现有机制满足；是否把内部状态泄漏给调用方，或为单个模型特例增加长期维护的公共表面。
- 类型、错误处理、所有权、线程与异步约定是否明确；检查源码与 ABI/API 兼容性及现有消费者，不照搬其他项目的 C/C++ API 政策。
- 新行为是否有真实调用或使用示例；文档、调用方及提交者验证材料是否匹配，不能只看接口声明。
- 涉及服务、调度或远端输入时，检查请求校验、取消与失败恢复、跨请求隔离和资源回收；信任代理头或反序列化字段需有明确边界。

## 通用规范与提交材料（每次）

- 分开检查行为与规范：命名、格式和文件组织以适用仓库规范及模块惯例为依据；个人风格偏好标为可选，同类问题合并。
- 注释是否解释非显然原因，是否与实现一致；清理临时调试、无用分支及失效说明，但不因文字风格不合偏好就认定缺陷。
- 新文件、依赖、抽象及公共表面是否有必要；没有检索现有机制前，不断言“项目缺少这个能力”。
- 提交者的测试代码是否覆盖修改行为、相关存量路径、边界及回归风险；所给结果是否注明版本、条件和适用配置，能否支持其主张。
- 缺少用例、文档或数据时，说明需要补充什么及原因。缺证不是代码错误的证明；是否必须修改取决于关键影响或明确规范，而非统一套用门槛。
