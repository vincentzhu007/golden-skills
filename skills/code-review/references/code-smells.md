# 代码坏味道：设计问题的线索

用于 MindSpore Lite LLM 变更及受影响存量模块的设计检视。下文是识别方向，不是在断言项目已有这些问题。

坏味道不是缺陷证明，也不是自动重构指令。先建立“代码现象 → 设计成因 → 本次变更的代价或风险 → 最小改进方向”的证据链，再按主技能的处理分类、来源及确信程度报告。没有具体代价时，不仅凭名称、参数数量、函数长度或嵌套深度下结论。

## 1. 散弹式修改

- **信号**：增加一种模型、配置或执行模式，要同步修改多处调度、Cache、配置及执行逻辑。
- **核实**：追踪同一语义决策的全部落点；区分必要的跨层接入与重复承担同一职责，指出遗漏同步修改的具体后果。
- **合理例外**：一个完整功能本就需要接口、实现、文档和用例配套，多文件不是坏设计的充分条件。
- **改进方向**：让同一变化拥有明确归属，通过既有契约传递能力或策略；不为消除文件数量而引入中央巨型管理器。

## 2. 重复条件判断

- **信号**：相同的模型、设备、量化或执行阶段判断散落多处，每次支持新组合都要逐个补分支。
- **核实**：条件是否真正表达同一能力，默认分支和支持集合是否一致；哪些位置已分歧，或本次修改为何要求同步维护。
- **合理例外**：看似相同的条件可能服务不同契约，设备局部特化也可能是刻意隔离。
- **改进方向**：收敛共同能力判定或分派归属，保留局部实现差异；不机械改成继承、策略类或查找表。

## 3. 数据泥团、参数膨胀与基本类型滥用

- **信号**：长度、偏移、位置等总是成组传递；持续增加布尔开关；不同语义都用整数或字符串，调用处难以辨认合法组合。
- **核实**：找出共同变化的参数、单位、范围及互斥关系；定位发生语义转换或重复校验的调用点，而非只数参数。
- **合理例外**：稳定的底层接口、设备 ABI 或简单的局部调用可以保留基本类型；配置对象也可能只是把混乱藏起来。
- **改进方向**：按稳定语义聚合参数，显式表达单位、模式和合法组合；说明收益及兼容成本，不要求额外分配或搬运数据。

## 4. 时间耦合

- **信号**：调用方必须记住“设置 A → 准备 B → 执行 C”，遗漏或重复调用只能靠约定避免。
- **核实**：阅读实际调用序列、失败和重试路径；查明顺序约束由谁维护，以及接口是否允许违反约束。
- **合理例外**：设备生命周期或分阶段执行可能天然有序；有明确状态机和受控入口时，分步接口不必合并。
- **改进方向**：让状态转换及合法操作归属清晰，必要时收敛入口或用类型表达阶段；不要只增加更多存活标志和防御分支。

## 5. 抽象泄漏与特性依恋

- **信号**：调用方读取另一模块的内部字段、布局或状态，并据此执行本应由被调用模块负责的逻辑。
- **核实**：指出调用方被迫知道的内部决策；分析内部变化会波及哪些消费者，行为应由谁拥有。
- **合理例外**：公开的张量布局、零拷贝视图或性能关键接口可能刻意暴露细节；需依据契约和代价判断。
- **改进方向**：把行为放回拥有相关知识的模块，暴露所需能力而非全部内部状态；避免为封装而复制数据或制造大量转发层。

## 6. 冗余状态与临时字段

- **信号**：长度、容量、有效 token 数等事实被多处保存；大量字段只在某个阶段有效，方法反复判定当前模式。
- **核实**：区分不同字段的真实语义；追踪更新、失败、重置及失效路径，检查缓存派生值是否有一致性机制。
- **合理例外**：缓存可避免热路径昂贵计算；相似字段可能分别表示逻辑长度与物理容量，不能合并。
- **改进方向**：明确事实来源与派生关系，集中必要更新或划分阶段职责；不要一概改成实时计算。

## 7. 发散式变化与过大职责

- **信号**：一个类同时因模型适配、内存分配、请求调度和设备执行而变化，各方法依赖不同字段集合。
- **核实**：通过调用与字段使用找出独立变化原因，解释本次变更为何牵动无关职责；不以类长或方法多作为结论。
- **合理例外**：薄的编排层可以协调多个模块，只要不吞并它们的内部决策；拆分也可能增加跨对象状态同步。
- **改进方向**：按独立职责和稳定契约拆分，保留清晰编排；比较拆分后的依赖与同步成本，避免产生碎片化小类。

## 8. 平行实现与复制变体

- **信号**：新增模型或后端复制整段流程，仅少数字段、条件或算子不同；修复需要在多个版本重复应用。
- **核实**：比较语义而非文本相似度，确认共享不变量及差异的演进方向，指出已有漂移或本次维护代价。
- **合理例外**：不同硬件约束、独立演进或性能特化可以合理重复；错误抽象比少量重复更难维护。
- **改进方向**：只提取稳定的共同决策或机制，保留差异；不要为了 DRY 合并整条路径或引入过宽参数化。

## 9. 推测式通用化

- **信号**：为尚不存在的模型或后端设计插件框架、多层策略、大量配置；当前调用仅使用一个组合。
- **核实**：先查明确需求和已有消费者，列出新增机制实际解决的问题及其维护成本；当前使用少不自动意味着无必要。
- **合理例外**：已承诺的扩展契约、外部消费者或稳定边界可能需要提前设计，不能要求看到仓库内调用才承认价值。
- **改进方向**：满足明确需求，复用已有扩展点，删除无依据的变化维度；若涉及削减需求，交由用户决定。

## 10. 补丁堆叠

- **信号**：每个异常情形再加一个标志位、特殊分支或重试，状态空间持续扩大。
- **核实**：追踪保护逻辑修补的共同不变量；判断是在表达真实差异，还是补偿错误的所有权、状态或错误传播设计。
- **合理例外**：兼容性和设备差异可能需要局部补丁；正确的边界校验也不是坏味道，不能为简洁删除必要保护。
- **改进方向**：修正共同成因，减少需要同步维护的状态；明确最小调整范围、行为保持要求及由提交者补充的回归证据。

## 如何形成意见

不要写：“这里重复代码，违反 DRY，建议抽象。”

可采用以下推导方式，但必须用真实位置与证据替换场景：两条路径维护相同 Cache 状态转换，本次新增状态需要同步修改，而失败分支的语义已有分歧；建议收敛共同状态转换的归属，保留不同后端执行细节。若尚不能证明两者契约相同，只提出待核实条件，不断言存在缺陷。

- 有充分证据的设计问题，即使行为正确也可归为“必须修改”；说明其阻塞依据及替代方案的代价。
- 本次变更加重存量问题时，要求最小必要调整；其他相关设计债作为建议，不扩展为全模块重构。
- 同一成因可能表现为多种坏味道，合并为一条意见，不按清单逐项凑数。验证仍由提交者执行，评审者不运行代码。
