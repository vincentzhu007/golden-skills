# 代码品味（写作期）

## 边界

- 管动手写之前的决策：数据形状、职责归属、错误模型、接口与性能假设。
- 不替代 `code-review`（评审期取证与分类）；不重复 lint 与 C++ 硬指标（CCN/NLOC/入参、格式），那些交给工具。
- 没有明确需求时不引入框架、扩展点或配置项。

## 工作流

1. **先定数据与所有权**：写出核心状态、生命周期和并发共享；用结构让非法状态无法表示，而不是补 if/else 和成对布尔。改功能时先判断是扩展既有结构还是新增第二套。
2. **先减后加**：删掉死代码、冗余校验、无消费者的扩展点，再在更小的基础上实现。满足当前明确需求，不为未确认的未来铺路。
3. **定错误模型**：在系统边界校验外部输入，内部信任类型。返回码还是异常、在哪里兜底，与项目既有约定一致，不新增第二套。
4. **定接口与命名**：让单位、模式、合法组合进类型或命名；调用方需要知道的越少越好。跨函数边界改动前先画类型与签名。
5. **性能是测量主张**：热路径的新增分配、复制、同步、重复计算，要么由执行路径证明必要，要么标注为待测假设，不写成结论。
6. **自检**：对照[设计品味目录](references/design-taste.md)检查是否引入坏味道，确认失败路径与回退。

## 完成标准

- 状态有单一归属，失败路径明确，合法组合由类型或结构约束。
- 没有投机抽象、平行实现，或只为消除文件数量的拆分。
- 性能主张有测量，或明确标注为假设。
